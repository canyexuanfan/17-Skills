# 技术细节：隐形盲水印的原理与边界

> 面向较真的用户 / 维权场景 / 疑难排查。结论先行：本技能的水印扛平台压缩、扛缩放回弹，**不扛裁剪、截图、AI 重绘**——所有实测数据见下，不夸大。

## 1. 算法原理（DWT-DCT-SVD）

`blind-watermark` 库（guofei9987/blind_watermark，MIT 协议）的嵌入流程：

```
原图 → 小波分解(DWT) → 选低频子带 → 分块 → 每块 DCT 变换
     → SVD 分解取奇异值 → 按水印比特流微调奇异值 → 逆变换重建图像
```

- 水印文本先按字符编码展开成比特流（"©十七° shiqidu@2026" = 184 bits），每 16 bit 一组带校验嵌入。
- 改动发生在**低频奇异值**上：人眼对低频不敏感（所以看不见），而压缩/缩放主要破坏高频（所以水印活得下来）。
- 提取是逆过程，**不需要原图**（盲提取），但需要两个参数：`password`（决定嵌入位置的伪随机序列种子）和 `wm_bits`（比特流长度）。

## 2. 密码与凭证

- `password_wm` / `password_img` 两个整数种子，本技能简化为一个 `--password`。
- 拿错密码提取 = 伪随机位置对不上 = 得到乱码（不会报错，看 match_ratio 判断）。
- 凭证三元组 `wm_text / wm_bits / password` 由嵌入方保存，等同私钥。**技能无法帮用户找回丢失的凭证**——没有暴力枚举，这是特性不是缺陷。

## 3. 鲁棒性实测矩阵（2026-09-29，本机 venv）

测试图 1200×800 彩条纹理 + 圆形主体，水印 "©十七° shiqidu@2026"（184 bits），password=7。

| 攻击 | 操作 | 提取 match_ratio | verdict |
|---|---|---|---|
| 无损拷贝 | PNG 直读 | 1.000 | match |
| 平台式二压 | Pillow 存 JPEG q85 | 0.941（"©"→乱码，17/18 字符正确） | match |
| 图床二压 | 缩 50% → 放回 1200×800 | 1.000 | match |
| 裁剪 | 裁掉顶部 160px + 右侧 240px（-20%） | 乱码 | no-match |
| 分辨率减半不回弹 | 缩 50% 直接保存 | 乱码 | no-match |

### 为什么裁剪扛不住？

DWT 低频子带是**全图整体**变换，裁掉一块后保留区域的低频相位结构已经改变，SVD 奇异值对不上嵌入时的块划分。官方 README 宣称的"50% 裁剪攻击可提取"在本版本（0.4.4）实测未复现——以实测为准，对外宣传不要写"抗裁剪"。

### 为什么"缩放后回弹"能扛？

压缩→下载原图→查看者再缩放的链路里，图片最终以某个分辨率被观看，盗图者通常会恢复到接近原始尺寸。只要整体像素结构还在（不裁剪），低频奇异值扰动就能被还原。

## 4. EXIF/tEXt 属性层细节

- JPEG：写入 EXIF `Artist(0x013B)` / `Copyright(0x8298)` / `ImageDescription(0x010E)`，其中 Description 追加 `|bits:N` 方便查验时自动读位长。
- PNG：写入 tEXt chunk `Artist` / `Copyright` / `WM_TEXT` / `WM_BITS`（Pillow PngInfo）。
- **平台剥离是合规行为**（尤其 GPS 类隐私），微信压缩发送、微博/小红书/公众号上传都会剥。属性层只对"文件级倒手"（网盘、邮件原图、拷贝）有效。

## 5. 清除的数学现实

盲水印是**加性频域修改**：`embedded = f(original, watermark)`。已知 embedded 反解 original 是欠定问题，没有无损逆运算。可行的清除只有两条路：

1. **持有原图**：直接用原图重出（本技能 `remove --mode from-original`），画质零损失——所以嵌入前保留无水印原图是唯一靠谱的习惯。
2. **破坏性抹除**：重采样 + 低通模糊 + 有损重编码，把低频结构搅乱到提取失败。画质有可见损失，`--scale/--blur/--quality` 可调平衡。

## 6. 已知坑（开发记录）

- `blind_watermark` 首次 import 会往 stdout 打欢迎语 → 必须 `bw_notes.close()`，否则 JSON 解析崩。
- `WaterMark` 对象 embed 后不可复用（库内部 in-place 修改）→ 每次操作新建实例。
- `wm_bits` 不要自己按"字符数×16"估算（本例 18 字符实际 184 bits，对不上）→ 一律用 embed 输出的真实值。
- opencv 在嵌入时可能打 `Unsupported depth image` warning 到 stderr → 无碍，stderr 已与 stdout 分离。
